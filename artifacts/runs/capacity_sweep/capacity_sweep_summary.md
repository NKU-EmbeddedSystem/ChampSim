# 实验阶段3：L2C 容量敏感性分析报告

## 实验目的

在不同的 L2 Cache Way 数配置下运行 trace，分析 trace 对 L2 容量变化的敏感性，判断是否存在 **"平坦区"（Flat Zone）**——即增加 L2 容量并不能带来 IPC 提升的现象。这是 EMISSARY 方案有效性的前提条件：如果 L2 的额外容量没有被充分利用，那么将这些冗余的 SRAM 重新分配给 EMISSARY I-cache 保护可能带来净收益。

## 实验方法

使用 `run_capacity_sensitivity.py` 脚本，对选定的 trace 在 5 种 L2 Way 配置下进行仿真：**L2W1、L2W2、L2W4、L2W8、L2W16**。每次仿真使用 LRU 替换策略，记录 IPC 和各级 Cache 命中率。

- 预热指令数：50,000,000
- 仿真指令数：500,000,000
- 测试 trace：6 个（barnes_1, facesim_1, fft_m24, radix_1, ocean_cp_1, streamcluster_1）

## 关键发现

### 1. 所有 6 个 trace 均处于 8W→4W 平坦区

在 8-way 到 4-way 的缩减中，**所有 trace 的 IPC 下降均 < 0.5%**，远低于 2% 的平坦区阈值。这意味着对所有这些 trace 而言，8-way L2 Cache 的上半部分（高 4 way）对性能的贡献几乎为零。

### 2. 极端平坦案例：radix_1 和 streamcluster_1

- **radix_1**：IPC 从 16W 到 1W **完全不变**（2.202），尽管 L2C 命中率从 50.0% 降到 10.9%。这说明 L2 命中率的提升完全被其他因素（如乱序执行的隐藏延迟能力、预取等）所抵消
- **streamcluster_1**：L2C 命中率在所有配置下都极低（0.4%~4.3%），说明该 trace 的访存模式完全不受益于 L2 Cache，IPC 也几乎不变

### 3. L2 命中率提升≠IPC 提升

barnes_1 从 1W 到 8W，L2 命中率从 41.5% 提升到 92.7%（提升 51 个百分点），但 IPC 仅从 2.205 提升到 2.231（提升 1.2%）。这说明：
- 大部分 L2 命中的访问本身就是对延迟不敏感的（如预取命中）
- 乱序执行核心能够隐藏大部分 L2 访问延迟
- L2 Cache 存在明显的**容量过剩**现象

### 4. 平坦区的普遍性

即使 IPC 对 L2 容量最敏感的 `fft_m24`，8W→4W 的 IPC 损失也仅 0.33%。这强烈表明：在 ChampSim 默认配置下，8-way L2 Cache 对于大多数 SPEC/科学计算类 workload 存在明显的容量冗余。

## 结论

1. **平坦区假设成立**：对于所有 6 个测试 trace，8-way L2 Cache 的上半部分（4 way）对 IPC 的贡献可忽略不计（<0.5%）
2. **EMISSARY 方案有可行性基础**：既然额外 4 way 的 SRAM 用于数据缓存几乎无益，将其重新分配给 EMISSARY 用于 I-cache 保护是一个有潜力的优化方向
3. **radix_1 和 streamcluster_1 是最理想的验证目标**：它们展现了最极端的平坦区特征，意味着如果用 EMISSARY 替代冗余的 L2 容量，任何 IPC 提升都会是纯收益
4. **需要注意**：平坦区仅说明额外 L2 容量对数据缓存无益，但并不保证 EMISSARY 的 I-cache 保护一定能带来 IPC 提升——这需要 I-cache miss 确实存在且是性能瓶颈
